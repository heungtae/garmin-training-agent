# U1 공통 교환 명세 — 기술 결정

- 단위: U1 `u1-exchange-spec` (`spec`), 기준일: 2026-11-18.
- 범위: 승인된 계약/기능 설계의 형식·무결성·호환 선택 6개를 근거·결과·대안과 함께 기록한다. 새 앱 언어/프레임워크·제품 DB·서비스·클라우드 선택이나 구현 승인이 아니다.
- 근거: [확인한 답변](nfr-requirements-questions.md), [교환 계약과 CD-ADR-001~003](../../../inception/contract-design/contract-summary.md), [기능 설계 WF1~WF7](../functional-design/functional-spec.md), [업무 규칙](../functional-design/rules.md), [상세 보안·품질 NFR](security-requirements.md).

## U1-TD-001 — 설명과 판정 자료

**배경:** 정확한 내용의 검토/승인과 서로 다른 클라이언트의 교환이 필요하다. CD-ADR-001과 C05는 JSON 완전본을 판정 기준, Markdown을 사람이 읽는 설명으로 정했다.

**결정:** Markdown으로 규범·오류·근거를 설명하고, 프로그램 판정과 합성 교환 자료는 UTF-8 JSON으로 정의한다. 단일 선두 BOM·바깥 공백/CRLF만 전송 허용 규칙으로 처리하고 문자열·한국어·인용부호·줄바꿈·불투명 ID의 의미를 보존한다. Markdown 편집·파일명·헤더·원격 수정 시각은 JSON 내용 승인/동일성을 대신하지 않는다.

**결과:** 설명과 기계 판정의 책임이 명확해지지만 JSON 완전본의 실제 생성/읽기/저장·승인 근거 연결을 검증해야 한다. ChatGPT 환경의 지원은 미검증이며 JSON 선택만으로 저장 경로가 확보되지 않는다. 문서/JSON 자유 서술의 민감성 검사는 별도로 남는다.

**대안:** Markdown 단독 기준은 정확한 wire 필수성/내용 결합에 부족하다. Sheets 행/표시값·Docs 본문 추출은 상류에서 비교한 대안이며 선택한 JSON 기준을 이 단계에서 바꾸지 않는다.

## U1-TD-002 — 등록 Schema와 참조

**배경:** C01/C02는 신뢰된 고정 bootstrap/registry와 실제 digest 대조를 요구한다. 미지 버전·임의 원격 스키마가 검증 기준을 바꾸면 권한/무결성이 흔들린다.

**결정:** Common·C01~C08의 정의 9개를 JSON Schema Draft 2020-12로 등록한다. C03 Detail은 같은 C03의 등록 fragment다. schema URI는 식별자이며 다운로드 지시가 아니다. 참조는 신뢰된 고정 로컬 registry에서 모두 해석한다. C01/C02 bootstrap과 Common은 소비자 설치/검증된 배포 경로에서 고정하고, RELEASE의 C03~C08 각각 한 번·schema/common/fixtures digest를 실제 자료와 대조한다. 구조 통과 후 BR/CR 의미 검사를 수행한다.

**결과:** 단위별 독립 검증과 재현 가능한 기준 선택이 가능하다. 구조만으로 기간/합계/최신성/승인/안전을 확인하지 못하므로 적격 의미 검증과 외부 차단을 별도 유지한다. 호환되지 않는 도구/미해석 참조는 성공 처리하지 않는다.

**대안:** 원격 자동 조회/최신 버전 추종은 불신 입력이 검사 기준을 바꿀 수 있다. 느슨한 최상위 필드 무시는 필수/권한 필드 우회를 허용한다. 검증기 독자 스키마는 U1과 소비자 사이의 이중 기준을 만든다.

## U1-TD-003 — 전체 JSON 무결성

**배경:** FR6.10·FR7.7, BR1.2·CR02는 버전·설명·가정·시각/정책까지 정확한 전체 내용을 승인 대상과 연결하도록 한다.

**결정:** 전체 payload의 RFC8785 JCS 정규화 UTF-8 바이트에 SHA-256을 적용한다. digest는 `sha256:`와 소문자 64자리 16진수다. 안내/가정/extensions도 제외하지 않는다. C06은 C05 또는 C07 전체와 C04 정책 digest, 정확한 사용자/행위/원 ArtifactRef를 대조할 후보를 표현한다. C06 자체·Markdown·헤더·파일명·원격 수정 시각을 C05 hash에 섞지 않는다. RELEASE의 fixturesDigest는 RELEASE를 제외한 U1 fixture 이름→전체 내용 11개 객체에 결합한다.

**결과:** 같은 논리 버전의 다른 내용과 검사 후 변경을 식별할 수 있다. digest 일치는 인증/인간 승인·정책 현재성·원격 저장 성공의 증명이 아니다. 일반 JCS Unicode/수치 경계 적격성이 필요하며, 한정 ASCII 속성·유한 정수·십진 문자열 사례의 결과로 일반 적격성을 선언하지 않는다. 승인 내용 변경은 새 버전/digest/승인으로 연결한다.

**대안:** 선택 필드만 hash하거나 문자열/파일명·수정 시각만 대조하면 설명/권한/시각 변경을 놓친다. 일반 JSON key 정렬 직렬화만으로 JCS 전체 적합을 주장하는 방식은 적격성을 입증하지 못한다. 비밀 키/모델 자기 서명을 추가해 승인을 대신하지 않는다.

## U1-TD-004 — 버전·호환과 소비자 증거

**배경:** WF1과 명세 변경 정책은 배포된 버전의 내용 교체, 검증 없는 새 버전 활성화와 승인 증거 전용을 금지한다.

**결정:** 현재 등록 1.0.0의 최종 배포 내용/digest를 고정하고 배포 후 같은 버전으로 교체하지 않는다. 허용 필드·승인/행위·단위·ID·의미·필수 구조 변경은 호환 파괴로 검토해 새 주요 버전과 소비자 합의를 요구한다. 공유 확대에는 별도 사용자 동의가 필요하다. U2/U3는 같은 고정 U1 릴리스에 각각 독립 부합하며, 실제 수행 scope/기대/관찰/증거만 연결한다. 미수행은 PLANNED/NOT_RUN, ConsumerBinding 증거 미확보는 UNASSESSED로 유지한다.

**결과:** 원격 자동 migration과 모호한 버전 병합을 피하지만 버전별 자료/소비자 부합 증거 관리가 필요하다. **ConsumerBinding에는 소비자 구현/워크플로 개정 식별이 충분하지 않은 승인된 미해결 위험이 남는다.** 따라서 고정 releaseId/assessmentRefs만으로 임의 소비자 개정별 완전 재현성을 주장하지 않는다. 검사 보고의 사용 가능한 프로필/한계를 명시하는 것은 기존 모델의 개정 식별 보완이나 해결 선언이 아니다. 기존 기능 모델은 이 단계에서 수정하지 않는다.

**대안:** 최신 버전 자동 활성화·같은 버전 덮어쓰기·과거 부합 결과 전용은 변경 영향을 숨긴다. 이 단계에서 ConsumerBinding 필드를 새로 추가하는 대안은 승인된 기능 모델 변경이므로 채택하지 않는다. CONFORMANT를 제품 활성화/전체 인수 권한으로 쓰지 않는다.

## U1-TD-005 — 도구 적격성과 구현 선택 책임

**배경:** JSON/Schema/JCS/십진수/시간대의 표준 이름만 정해도 모든 도구가 필요한 의미를 지원하는 것은 아니다. U1은 spec이며 앱 구현 언어를 선택할 단위가 아니다.

**결정:** U1은 아래 형식/호환/검사 적격 조건을 정의한다. 구체 라이브러리·버전·설정/빌드·유한 자원 값·실행 장비는 각 소비자 구현 담당이 NFR Design/구현에서 선정하고 실제 검사 프로필로 남긴다. U2의 기존 Rust 제약을 U1 검증 도구/앱 언어의 신규 선택으로 전용하지 않는다. 도구 미확보/미적격은 미수행/보류다.

| 도구 역할 | 적격 조건 | 책임·미검증 범위 |
|---|---|---|
| 바이트/JSON 파서 | UTF-8·중복 키 탐지·단일 객체·후행 입력/NaN/Infinity/잘림 거절, 문자열 보존, 파싱 전/도중 유한 바이트/깊이 한도 | U2/U3가 실제 라이브러리/버전/한도 경계 증거 확보. 이 문서는 구현하지 않음 |
| Schema 검사 | Draft 2020-12 및 등록 `$ref`/fragment·필수/null·열거·additionalProperties/allOf/조건 검사를 지원. format 검사 여부를 명시하고 날짜/시각 의미를 별도 검증 | U1 기준과 소비자 독립 사례 일치. format annotation만으로 실제 일자/시간대 검증 완료 주장 금지 |
| JCS·SHA-256 | 전체 payload 정규화·Unicode/수치 경계·잘못된 Unicode 거절의 적격 증거, 고정 기대 digest 대조 | U1 규약/일반 적격 조건, U2/U3 실제 도구 선택/실행. 단순 키 정렬로 대체 금지 |
| 십진 계산/상태 의미 | 확정 GTA-NUMERIC-1의 정확 합계/유리수 중간값·속도/페이스 최종 6자리 HALF_EVEN·wire 정규형 정확 대조·30+18/256자리 한도·분모0·7상태/우선순위를 보존 | U2/U3 실제 계산 도구의 NUM-01~16 및 근거/척도 부합 증거 필요. 수치 규범을 소비자별로 재선정하지 않으며 생리적 임계값은 별도 |
| 일자/시간대 | 실제 IANA 시간대·적격 tzdbVersion, 시작 포함/끝 제외·오프셋·DST 모호/누락 시각 보류 | U2/U3 데이터/버전 선정·실제 집계/게시 검증. 적격 tzdb 미확정 유지 |
| 적합성 검사/보고 | 고정 릴리스/입력/변형/BR/NFR/scope/프로필·기대/관찰/증거·미수행·외부 차단 구분, 합성 비밀 출력 제외 | U1 공통 기준, 소비자 독립 실행. ConsumerBinding 개정 식별 한계 유지 |

**결과:** 제품 언어/공급자 라이브러리와 U1 규범을 분리하고 미적격 도구의 조용한 통과를 막는다. 적격 도구·버전과 실제 한도 확보는 여전히 후속 작업이다. 이번 문서 작성에 새 인터넷 조사·패키지 설치·표준 구현 코드를 추가하지 않는다.

**대안:** 특정 SDK·언어/라이브러리 이름을 표준 적격의 충분조건으로 쓰거나, 한정 합성 스크립트를 일반 JCS/시간대/의미 검증기로 간주하면 실제 지원 차이를 숨긴다. 새 검증 프레임워크/DB/서버를 U1 필수로 만드는 것은 현재 단위 범위를 넘는다.

## U1-TD-006 — 독립 명세 경계와 실행 책임

**배경:** 단위 DAG와 C01/C02는 U2/U3가 U1에 의존하고 각자 독립 부합하도록 한다. 왕복 교환 자료는 빌드 역의존을 허용하는 근거가 아니다.

**결정:** U1은 Common·C01~C08과 공통 합성 fixture/사례·기대값만 소유한다. U2 전용 EVALUATION·LLM_REQUEST·LLM_RESPONSE·공급자 SDK/프로필·실행 파일/DB, U3 전용 자료/실제 워크플로 실행을 U1 자체 검증의 필수 의존에 넣지 않는다. U1에 앱 프레임워크·제품 DB·상시 서버·클라우드·운영 SLA/SLO/대시보드를 선택하지 않는다. 실제 권한·정책 최신성/철회·승인/안전·저장/수신/Calendar·모델/처리 위치/비용·자원은 원 실행 소유자가 실제 증거로 적격화한다.

**결과:** U1 기준을 공통으로 제공하면서 구현/실제 제품 인수와 명세 정합을 구별할 수 있다. 합성 적합성은 미해소 C04/C06/C07·C08·P01~P05를 해소하지 않는다. Ollama 제외·원격 초기 OpenAI 대상·로컬/사설 미정 등 상류 결정도 그대로 유지한다. U1 보안/품질 NFR에 관련 무결성/시간/증거를 연결하고 실제 지연/바이트/깊이/호출/비용 수치는 실행 단위로 넘긴다.

**대안:** U2/U3 완성 후에만 U1 검증, 공급자 SDK로 공통 명세 생성, U1의 외부 계정/서비스 호출을 자체 부합 조건으로 삼는 방식은 독립 검증과 소유 경계를 깨뜨린다. 명세 통과를 실제 사용자 승인/연동 성공으로 취급하지 않는다.

## Assumptions & Open Questions

신규 앱 기술/외부 지원을 가정하지 않았다. 실제 승인 프로필·원 정책 현재성/철회·ChatGPT 지원/지속 저장·Drive/GitHub/Calendar 권한과 결과 대조·Garmin 상세 계약·안전·원격 모델 및 로컬/사설 처리/하드웨어/비용·자원/정밀도/tzdb 적격성은 [보안·품질 문서의 미해소 표](security-requirements.md)에 따라 보류/인계한다. ConsumerBinding 개정 식별 한계를 포함한 승인된 기능 설계 위험은 해결된 것으로 바꾸지 않는다.

별도 성능/확장/신뢰성/운영 관측 문서를 요구하지 않는 U1 kind 범위를 유지한다. 추가 법정/보안 인증이나 공개 배포 완료를 선언하지 않는다. 이 결정 기록은 새 제품 코드·SQL·패키지 설치·실제 외부 호출·제품 검증 실적을 포함하지 않는다.
