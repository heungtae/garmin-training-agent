# Garmin Training Agent 구현 단위 정의

- 작성일: 2026-11-17
- 근거: [컴포넌트 목록](../domain-design/components.md), [도메인 ADR](../domain-design/decisions.md), [상세 요구사항](../requirements-analysis/requirements.md), [단위 계획과 확인 답변](units-generation-questions.md).
- 목적: 승인된 책임을 구현·검증·배포 관점의 3개 단위로 구체화한다. 현재 결과는 설계 문서이며 코드·설치물·외부 연동 결과는 없다.
- 관련 문서: [의존 관계](unit-of-work-dependency.md), [요구사항별 배정](unit-of-work-story-map.md), [추적성](traceability.json).

## 단위 목록

| Unit ID | Directory | Kind | 설명 | 배포 형태 | 상대 복잡도 |
|---|---|---|---|---|---|
| U1 | u1-exchange-spec | spec | 공통 교환 명세·호환 기준·합성 사례 | shared: 소비자가 버전을 지정해 참조하는 명세 산출물 | L |
| U2 | u2-linux-agent | service | Rust 설치형 프로그램과 7개 내부 컴포넌트 | standalone: 한 PC의 설치형 실행 프로그램, 내부 모듈은 embedded | XL |
| U3 | u3-chatgpt-workflow | spec | ChatGPT 목표·계획·승인 의사·저장 워크플로 정의 | shared: 실제 지원되는 클라이언트 경로가 읽어 사용하는 정의/안내 | L |

`Directory`는 단위의 안정적인 이름이며 후속 단위별 설계 기록은 `construction/<Directory>/` 아래에 생성된다. 구현 소스 경로·패키지 형식은 이 표로 확정하지 않는다. 복잡도는 단위 내부 규칙·외부 검증·실패 상태의 상대 크기이며 기간·개발 순서·인력 추정이 아니다.

## U1 — u1-exchange-spec

### 책임과 산출물

- 분석 자료·탐색 안내·서비스별 허용 정책·목표·계획·세션·승인 의사·저장/수신/게시 결과의 공통 교환 명세를 관리한다.
- 원천·기간·단위·시간대·버전·완전성·누락/0/추정 구별과 고유 식별·개정 연결·행위 범위를 명세한다.
- 합성 정상/오류/부분 작성/구버전/허위 수치/공유 금지 사례와 예상 판정을 제공한다. 특정 사용자·실제 건강 자료·비밀정보를 포함하지 않는다.
- 소비자 호환성과 명세 변경 판별 기준을 기록한다. 실제 Drive 문서 형식·내용 동일성·승인 증명·최신성 계약은 Contract Design에서 근거와 함께 선정한다.

### 소유와 경계

U1은 교환 정의와 합성 사례의 소유자다. 도메인 엔티티는 U2/U3의 원래 컴포넌트가 소유한다. AuthoredPlanVersion과 AdmittedPlanSnapshot 등 작성본/검증 사본의 의미·출처·소유 경계를 명세하며 업무 상태를 생성하거나 변경하지 않는다.

U1 산출물은 양쪽 소비자의 호환 기준이다. 제공자별 외부 API 어댑터, 실제 승인 증명 검증 실행, 외부 저장·게시, LLM 호출은 각 실행/작성 책임 단위가 수행한다. 비밀 보관 참조는 외부 교환 자료에 포함하지 않는다.

### 자체 검증과 제약

U2/U3 구현이 없어도 명세의 일관성·식별/버전 참조·정상/음성 사례·개인정보 제외를 검사할 수 있어야 한다. 소비자 구현의 실제 동작이나 권한 성공은 U1의 통과 기준으로 주장하지 않는다. Contract Design에서 승인 신뢰/정책 최신성을 만족할 계약을 구성할 수 없으면 미충족을 표시하고 관련 자동화를 보류한다.

담당 기능 요구사항은 30개 행이며 행별 **명세 부분**만 담당한다. 형식별 검증 도구·호환 범위·제약값은 후속 명세에 연결한다. 상대 복잡도 L은 승인 신뢰·버전 호환·불완전/위험 입력의 계약 난이도에 근거한다.

## U2 — u2-linux-agent

### 책임과 산출물

- OperationControl의 CLI·초기 설정·설치/제거·두 예약 주기·로그아웃 중 실행·즉시 실행·중복 제어·재개와 결과 집계를 제공한다.
- DataAccessPolicy의 연결·인증정보 보호 참조·권한·서비스별 공유/보존 정책을 적용한다.
- ActivityCollection의 Garmin 운동 수집·수정·정규화·중복 방지·완전성과 로컬 우선 보존을 구현한다.
- AnalysisPublication의 기간별 요약·구조화 자료·독립 GitHub/Drive 게시·충돌·재시도를 구현한다.
- PlanAdmission의 Drive 자료 수신·완전성·버전·승인 근거·안전 검증과 스냅샷/최종 적격 판단을 구현한다.
- PlanEvaluation의 원격 및 로컬/사설 OpenAI 호환 연결 유형·허용 입력·결과 검증·제안/실패 상태를 구현한다.
- CalendarDelivery의 승인 세션 게시·변경·취소·연결 상태·사용자 수정 충돌·응답 유실·부분 실패 복구를 구현한다.

### 배포와 모듈 소유

Rust 기반 설치형 실행 프로그램 안에 7개 컴포넌트를 모듈로 둔다. 별도 상시 클라우드나 컴포넌트별 네트워크 서버를 필수로 도입하지 않는다. 각 엔티티와 불변식은 원 소유 모듈만 변경하며 다른 모듈은 정의한 계약을 사용한다. 물리 저장·프레임워크·예약 실행 수단·설치 패키지·비밀 보호 수단은 NFR 설계에서 선택한다.

단위 범위에는 설치/배포에 필요한 산출물도 포함한다. 별도 packaging 단위를 추가하지 않는다. Linux 1차 환경은 Ubuntu 24.04 이상이며 로그아웃 실행을 실제 환경에서 검증해야 한다. PC 종료·절전 중 실행은 보장하지 않고 복귀 후 누락을 재검사한다.

### 자체 검증과 제약

U1의 고정 버전 명세·합성 사례와 외부 서비스 대역으로 자체 빌드/단위/내부 통합·복구 검증을 수행할 수 있어야 한다. U3의 워크플로 정의나 그 디렉터리의 테스트 자료를 필수로 가져오지 않는다. 실제 API·권한·로그아웃 실행 검증은 대역 결과와 따로 증거를 남긴다.

실제 연결 시험에는 허용된 테스트 계정·목적 범위의 자료만 사용하고 저장소 증거는 합성·익명화한다. 미지원 지표·키 참조 이름 GARMIN_API_KEY·미검증 인증 계약을 구분하며 키 값을 읽거나 문서에 담는 작업은 이 설계 범위에 없다.

승인 검증·게시 적격 판단은 정확한 버전/내용/허용 행위에 결합한다. 평가 호출 실패는 기존 사용자 승인·형식·안전 검증을 통과한 변경 없는 버전에 한해 고지 후 게시할 수 있다. 오류 결과·미승인 변경·안전 경고를 적용하는 우회 경로로 사용하지 않는다.

담당 기능 요구사항은 66개 행이다. 상대 복잡도 XL은 7개 업무 모듈과 여러 외부 연결·실패/복구 경계 때문이다. 세부 기능별 내부 작업을 나눌 수 있지만 단위 소유·배포 경계 변경은 계획 재검토 대상이다.

## U3 — u3-chatgpt-workflow

### 책임과 산출물

- CoachingWorkflow의 자연어 목표 등록·기존 기록 확인·구조화 요약·러닝 계획 작성·수정·명시적 승인 의사 수집·Drive 저장 결과 확인을 정의한다.
- 이미 제공된 정보 재사용, 불충분 자료의 추가 확인, 근거·가정·불확실성·고정 운동·회복 설명을 정의한다.
- 정확한 작성 버전에 승인 의사를 연결하고 새 버전에는 새 승인을 요청한다. 파일의 approved 표기를 검증 완료한 게시 권한으로 간주하지 않는다.
- 실제 계정·웹/모바일별 읽기·쓰기·실행 가능 범위와 검증된 수동 저장 대안을 안내한다. 성공 확인 전 저장 완료를 말하지 않는다.
- 외부 자료를 불신 데이터로 다루고 서비스별 허용 범위·동의 철회를 준수한다. 최신 정책을 신뢰성 있게 확인할 수 없으면 관련 전송을 보류한다.

### 배포와 소유

CoachingWorkflow가 소유한 목표·작성 계획·세션·승인 의사·저장 결과·처분 요청의 의미를 유지하는 워크플로 정의를 소비 환경에 제공한다. 실제 등록·전달 방식, 클라이언트별 도구 기능과 저장 형식은 계약 설계에서 확인한다. 이 kind는 별도 모바일 앱·상시 서버·로컬 프로그램 호출 기능을 추가하지 않는다.

DataAccessPolicy 엔티티의 원 소유자는 U2다. U3는 명세된 허용 정책 자료/사용자 확인을 소비하며, 해당 엔티티의 별도 권위 있는 사본을 만들거나 금지 범위를 임의로 완화하지 않는다. 정책 확인 경로의 신뢰·최신성은 후속 계약의 차단 조건이다.

### 자체 검증과 제약

U1의 명세·합성 분석 자료·목표/계획·정책·승인 사례를 사용해 워크플로의 분기·대화·작성 결과·성공 표현·제한 안내를 검증한다. U2 실행 파일·원천 DB·그 단위의 내부 코드나 테스트 자료를 자체 검증의 필수 조건으로 삼지 않는다. U1에 없는 U3 전용 자료는 U3가 소유하되 U2 테스트가 이를 숨은 의존으로 가져오지 않도록 한다.

이 검증은 실제 ChatGPT 도구 지원·쓰기 권한·사용자 승인 근거의 신뢰를 증명하지 않는다. 실제 환경 검증은 허용 범위의 합성 자료로 수행해야 한다. 지원되지 않는 경로에서 자동 저장을 약속하지 않고, 수동 대안도 승인 검증을 충족하지 못하면 보류한다.

담당 기능 요구사항은 33개 행이다. 상대 복잡도 L은 대화·데이터/승인 의미·환경별 읽기/쓰기와 대안의 검증 난이도에 근거한다.

## 공통 검증과 제품 인수 경계

| 검증 종류 | 책임과 범위 | 완료 해석 |
|---|---|---|
| U1 명세/합성 사례 정합 | U1이 소비자 구현 없이 정의·버전·오류 사례·비밀 제외 검사 | 공통 교환 명세의 일관성 |
| 단위 자체 코드/정의 검증 | U2·U3가 각각 U1과 자기 코드/정의·허용 대역으로 검사 | 각 단위가 맡은 부분의 동작 |
| 계약 호환성 | 같은 U1 버전의 사례에 U2·U3가 각각 부합하는지 대조 | 저장 자료의 호환 가능성; 실제 권한/승인 신뢰의 별도 증거 필요 |
| 전체 실제 인수 | 실제 지원 환경에서 U2 분석 게시→U3 목표·계획·승인·저장→U2 수신·검증·LLM·Calendar를 확인 | 적용 P0 전체와 실제 연동 성공의 제품 판정 근거 |
| 장애/권한·공유/중복/충돌 | 관련 소유 단위가 부분 실패·응답 유실·미지원·금지 공유·구버전 등으로 검사 | 기존 유효 자료 보존·오류 상태·복구·행위 차단 증거 |

현재 어떤 제품 시험도 실행/통과한 것으로 기록하지 않는다. 전체 실제 인수에는 원격 및 로컬/사설 LLM 유형 모두, Ubuntu 로그아웃 실행, ChatGPT 환경별 실제 지원과 신뢰성 있는 승인 근거가 포함된다. 한 단위의 자체 합격만으로 전체 P0 완료를 선언하지 않는다. 교환 명세의 판정 사례를 구현에 맞춰 완화해 실패를 숨기지 않는다.

## UG-ADR-001 — 3개 단위의 배포·검증 경계

### Context

도메인 ADR-001~004는 8개 책임과 단일 소유·비동기 자료 교환·승인/평가/게시 분리를 정했다. 한 PC의 개인용 운영 단순성과 서로 다른 ChatGPT 실행 환경, 양쪽이 공유할 계약의 독립 변경/검토를 함께 고려해야 한다. 요청자는 단위 Q1 A안과 Approve Plan, 작성 전 요약을 확인했다.

### Decision

공통 명세 U1(spec), 7개 모듈을 포함하는 Linux 설치형 U2(service), CoachingWorkflow의 U3(spec)로 묶는다. U2/U3는 U1에 빌드/테스트 의존하며 상대 구현을 자체 검증의 필수 조건으로 두지 않는다. 실제 배포물의 파일 형식과 실행 수단은 후속 단계에서 구체화한다.

### Consequences

공통 명세와 두 소비자의 호환성을 별도로 검토할 수 있다. Linux 운영 단위는 하나로 유지되지만 내부 모듈 소유 경계와 외부 실패 격리를 구현해야 한다. 교환 계약의 변경 시 영향과 소비자 부합성을 추적할 비용이 생긴다. 정책/승인 신뢰·최신성 미확인은 관련 전송/게시를 보류하며 새 서버·권한을 자동으로 추가하지 않는다.

### Alternatives Rejected

- **2개 단위:** 공통 명세를 Linux 단위에 둔다. 단위 수는 줄지만 명세 변경과 소비자 검토가 실행 단위에 결합되고 워크플로 검증이 그 산출물에 의존한다.
- **8개 단위:** 각 책임을 service/spec/library로 나눈다. 세밀한 코드·테스트 경계는 얻지만 라이브러리 버전·공통 자료형·빌드 의존 관리와 단위별 설계 부담이 커진다.
- 선택한 배포 묶음은 도메인 엔티티 소유나 P0 요구사항을 바꾸지 않는다. 향후 변경은 관련 계약·의존·매핑과 함께 재검토한다.

## 다음 단계에 넘기는 조건

Contract Design은 U1의 교환 계약과 양쪽 소비/생산 경계를 상세화한다. 승인 증명·내용 결합·Drive 형식·정책 최신성·서비스 권한·오류 의미를 검증 가능하게 정하고 불가한 경로는 보류한다. Functional/NFR 설계는 kind별로 필요한 데이터/업무/기술 산출물을 작성한다. 실행 기술·외부 제공자·처리량/지연·재시도·설치 수단의 미결정을 여기서 확정하지 않는다.

의존 관계는 [unit-of-work-dependency.md](unit-of-work-dependency.md), 기능 83개 및 NFR 11개의 배정은 [unit-of-work-story-map.md](unit-of-work-story-map.md)에 기록한다. 이 문서에는 경제적 개발 순서·기간·인력 배정·중요 경로를 정하지 않는다.
