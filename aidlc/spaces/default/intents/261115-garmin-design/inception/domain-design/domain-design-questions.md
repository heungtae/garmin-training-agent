# 도메인 설계 확인

## 입력과 유지할 결정

[승인된 상세 요구사항](../requirements-analysis/requirements.md)을 기준으로 논리적 기능 경계와 데이터 소유자를 정한다. 개인용·한 PC·러닝 우선·전체 P0·외부 지원 미검증 및 이번 단계까지 확정한 승인/공유/실패 정책을 유지한다. 배포 단위는 Units Generation에서, API·Drive 형식·승인 증명 방식은 계약 설계에서 결정한다.

## 설계 작업 계획

1. 선택한 분해안에 따라 각 기능의 책임·호출 관계·외부 의존성을 정리한다.
2. 엔티티마다 소유자를 하나씩 지정한다. 이 단계에서는 식별자·속성 이름·다른 컴포넌트 참조만 기록하고 자료형·검증값·관계 수는 기능 설계로 넘긴다.
3. 계획 작성 결과와 수신 후 검증한 스냅샷을 구분하고, 승인 근거·평가 결과·일정 게시 상태가 서로 대체되지 않도록 한다. 구체 승인 검증 방식은 미정으로 유지하며 신뢰성 검증 전 자동 게시를 허용하지 않는다.
4. 기능별 실패/충돌 책임과 비순환 호출 관계를 정하고, 상호 호출·데이터 소유 중복·요구사항 누락을 검사한다.
5. components.md의 YAML 목록·도표·소유 표, decisions.md의 대안 비교 ADR, traceability.json의 요구사항 연결을 작성하고 검토한다.

## Q1. 기능 책임을 어떤 경계로 나눌까요?

A. 8개 책임으로 분리한다: 운영 제어(OperationControl), 연결·공유 정책(DataAccessPolicy), 운동 수집(ActivityCollection), 분석 자료·저장소 게시(AnalysisPublication), 목표·계획 작성(CoachingWorkflow), 계획 수신·승인 검증(PlanAdmission), LLM 평가(PlanEvaluation), Calendar 게시(CalendarDelivery). 작성과 수신 검증, 평가와 게시를 각각 독립적으로 검토하기 쉽지만 경계 간 계약이 늘어난다. 프로그램의 배포 묶음은 다음 단계에서 정하며 경계 변경 시 소유 데이터·계약을 함께 조정할 수 있다. 위험 우선 및 승인 통제 요구사항에 맞아 권장한다.
B. 6개 책임으로 묶는다: A안에서 운영 제어와 연결·공유 정책을 합치고, 목표·계획 작성과 계획 수신·승인 검증을 합친다. 경계 간 계약은 줄지만 설정·공유 권한 및 작성·검증 책임을 각 내부에서 엄격히 구별해야 한다. 추후 분리 시 소유 데이터·계약 이동이 필요하다.
C. 4개 책임으로 넓게 묶는다: 운영·권한, 운동 수집·분석·저장소 게시, 목표·계획 작성·수신 검증·평가, Calendar 게시. 초기 목록은 간단하지만 한 경계의 변경·테스트 범위가 커지고 승인/평가 및 대상별 실패 격리를 내부 규칙으로 관리해야 한다. 추후 세분화 시 데이터 소유를 재분배해야 한다.

## Consolidated Summary Confirmation

- 승인된 요구사항과 P0 범위를 유지하고 8개 논리적 컴포넌트로 책임을 나눈다. 실제 배포 묶음·기술 선택은 후속 단계에서 결정한다.
- OperationControl은 CLI 설정·예약 실행·중복 실행 제어·실행 결과를 맡는다. DataAccessPolicy는 서비스 연결·인증정보 참조·공유 동의와 허용 범위를 맡는다.
- ActivityCollection은 Garmin 운동 기록·수집 진행 상태·원천 수정 처리를 맡는다. AnalysisPublication은 운동 자료의 기간 요약·분석용 산출물·GitHub/Drive 대상별 게시 상태와 충돌을 맡는다.
- CoachingWorkflow는 목표 입력·계획 초안/개정·사용자 승인 의사 수집·Drive 저장 결과 확인을 맡는다. PlanAdmission은 Drive 계획의 수신·완전성/버전/승인 근거 검증·수신 후 보존하는 검증 스냅샷과 게시 적격 판단을 맡는다.
- 계획 작성본과 수신 후 검증 스냅샷을 구분하고, 각 엔티티에는 소유자를 하나만 둔다. 다른 컴포넌트는 참조나 계약을 통해 조회·처리하며 소유 데이터를 직접 변경하지 않는다. 속성 이름·식별자·참조까지만 정하고 자료형·검증값·관계 수는 기능 설계로 넘긴다.
- PlanEvaluation은 허용된 자료에 대한 LLM 평가·조정 제안·평가 실패를 맡는다. CalendarDelivery는 검증된 승인 버전의 세션 게시·연결 상태·사용자 수정 충돌·변경/취소·재시도를 맡는다.
- 사용자 승인·저장·수신 검증·LLM 평가·Calendar 게시 결과를 구분한다. 평가 결과는 자동 승인이나 계획 변경 권한이 되지 않는다. 평가 실패 시 게시 허용 정책은 기존에 승인·형식·안전 검증을 통과한 변경 없는 정확한 버전에만 적용한다.
- 구체 승인 증명·Drive 문서 형식·API 계약·외부 권한/지원 여부는 미검증으로 유지한다. 신뢰성 있게 승인 근거를 검증하지 못하면 자동 게시를 보류한다. ChatGPT와 설치 프로그램은 Drive 매개 전달을 사용하며 직접 실행을 필수로 두지 않는다.
- 컴포넌트 목록·엔티티 소유·의존 관계·다이어그램과 텍스트 설명, 대안 비교 ADR, 요구사항 추적 목록을 작성한다. 호출 관계는 비순환으로 설계하고, 외부 서비스·저장 장치는 각 컴포넌트의 의존 대상으로 표시한다. 각 처리 단계의 실패/복구 상태는 해당 책임 소유자가 유지한다.
